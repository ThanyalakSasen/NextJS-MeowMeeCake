## 1. Flow ทั้งหมด (หลังแก้ครบ 8 ข้อ)

### 1.1 ภาพรวม

```
 แอดมิน                          ลูกค้า                          ระบบ (⏱ = cron ทุก 15 นาที)
 ─────                          ─────                          ────
 ① สร้างสินค้าพรีออเดอร์
   (is_preorder: true + preorder_config)
 ② สร้างรอบ + ใส่สินค้า + โควตา
   (scheduled | open)                                           ⏱③ ถึง open_date → เปิดรอบเอง (scheduled→open)
                                ④ ดูรอบ (catalog)
                                ⑤ สั่งพรีออเดอร์ ─────────────▶ จองโควตา (commitQty แบบ atomic)
                                                                ตั้งกำหนดชำระ = min(สั่ง + 24 ชม., ปิดรอบ)
                                                                แจ้งร้าน + ลูกค้าทาง LINE
                                ⑥ แนบสลิป ─────────────────────▶ แจ้งร้าน "สลิปรอตรวจ"
 ⑦ ตรวจสลิป → paid ─────────────────────────────────────────────▶ auto-confirm + แจ้งลูกค้า
                                                                ⏱ เลยกำหนดชำระ + ไม่จ่าย + ไม่มีสลิปรอตรวจ
                                                                   → ยกเลิกอัตโนมัติ (คืนโควตา + แจ้งลูกค้า)
                                                                ⏱⑧ เลย close_date → ปิดรอบเอง (หรือแอดมินกดปิด)
                                                                   → ยกเลิกทุกคนที่ยังไม่จ่าย (ยกเว้นสลิปรอตรวจ)
                                                                   → ⑨ สร้างใบสั่งผลิตอัตโนมัติ (นับเฉพาะ paid)
                                                                      วันผลิต = วันรับ − lead time สูงสุดในรอบ
                                                                   → แจ้งร้าน (สรุป)
 ⑦' ตรวจสลิปที่ค้างหลังปิดรอบ → paid ──────────────────────────▶ บวกจำนวนเข้าใบผลิตเดิม (ถ้ายัง planned)
                                                                ⑩ เตือนลูกค้าก่อนวันรับ (cron วันละครั้ง — LINE.md §9.7)
 ⑪ เปลี่ยนสถานะ preparing → ready → completed ──────────────────▶ แจ้ง ready (รับเอง) ทาง LINE
    (หรือจัดส่ง shipping → delivered)
```

### 1.2 สถานะรอบ (`round_status`)

```
 scheduled ──▶ open ──▶ closed
     │           │  ◀──────┘  (เปิดกลับได้ ถ้ายังไม่มีใบสั่งผลิต — ประเด็น 8)
     └─────┬─────┘
           ▼
       cancelled          (cancelled = จบแล้ว → ยกเลิกพรีออเดอร์ที่ค้างทั้งหมด + คืนเงิน — ประเด็น 1)
```

- **เปลี่ยนเองตามเวลา** (⏱ `runRoundScheduler`): `scheduled` + ถึง `open_date` → `open` · `open`/`scheduled` + เลย `close_date` → `closed`
  แอดมินยังกดเองได้ทุกขั้นเหมือนเดิม
- `closed` (มือหรืออัตโนมัติ) → ยกเลิกคนไม่จ่าย + สร้างใบสั่งผลิต (`onRoundClosed` — §6.3)
- ตอนสร้าง: `open_date` อยู่ในอนาคต → `scheduled` · ไม่งั้น → `open`
- ลูกค้าสั่งได้เมื่อ **ครบทุกข้อ** (`assertRoundOrderable`): สถานะ `open` · ถึง `open_date` แล้ว · ยังไม่เลย `close_date`

### 1.3 ลำดับวันที่ของรอบ

`open_date` < `close_date` ≤ `pickup_date` · และ `pickup_date − close_date ≥ lead_time_days` ของทุกสินค้าในรอบ (ประเด็น 2)

### 1.4 สิ่งที่ตรวจตอนลูกค้าสั่ง (`createPreorder`)

| ตรวจ | ที่มา |
|---|---|
| รอบรับสั่งได้ตอนนี้ | `assertRoundOrderable` |
| รายการอยู่ในรอบนี้ + `is_active` + ไม่ซ้ำ | `getOrderableRoundItems` |
| จำนวน ≥ ขั้นต่ำ = **max(ขั้นต่ำของรายการในรอบ, `preorder_config.min_order_qty`)** | 🆕 ประเด็น 2 |
| ยอดรวมของลูกค้าคนนี้ในรอบนี้ ≤ **`preorder_config.max_order_qty`** | 🆕 ประเด็น 2 |
| ไม่เกินโควตาคงเหลือของรอบ (`max_qty_total`) — จองแบบ atomic | `commitQty` |
| บันทึก **`payment_due_at`** = min(สั่ง + `PREORDER_PAYMENT_DEADLINE_HOURS`, ปิดรอบ) | 🆕 ประเด็น 3 |

## 3. วิธีแก้ (ก่อน → หลัง)

### 3.1 ปัญหา 1 — ยกเลิกรอบ → ยกเลิกพรีออเดอร์ที่ค้างทั้งหมด

| | ก่อน | หลัง |
|---|---|---|
| `PATCH /api/admin/preorder-rounds/[id]/status` `{ round_status: "cancelled" }` | บันทึกสถานะรอบอย่างเดียว | บันทึกสถานะรอบ **ก่อน** (ลูกค้าสั่งเพิ่มไม่ได้ทันที) แล้วไล่ `cancelPreorder` ทุกพรีออเดอร์ที่ยังไม่ `cancelled`/`completed` |
| พรีออเดอร์ในรอบ | ค้าง pending/confirmed ตลอด — สร้างใบผลิตไม่ได้ (ต้อง closed) · ลบรอบไม่ได้ (ยังมีค้าง) · ไม่ถูกเตือนก่อนวันรับ | ยกเลิก + เหตุผล `ร้านยกเลิกรอบพรีออเดอร์ "<ชื่อรอบ>"` |
| โควตา | ค้าง | คืน (`releaseQty`) |
| เงินที่ลูกค้าจ่ายแล้ว | ไม่คืน | **คืนอัตโนมัติ** (`registerAutoRefundOnCancel` — ผู้ยืนยันคือแอดมินที่กดยกเลิก) |
| ลูกค้า | ไม่รู้ | ได้ LINE "ถูกยกเลิก + เหตุผล" และ "คืนเงินเรียบร้อยแล้ว" (ถ้าผูก LINE — LINE.md) |
| Response / audit | รอบอย่างเดียว | + `cancel_cascade: { cancelled: [preorder_no…], failed: [{ preorder_no, error }] }` · audit log บันทึกจำนวน |

- ทำทีละรายการ **best-effort**: รายการไหนพังไม่หยุดรายการอื่น → อยู่ใน `failed` ให้แอดมินจัดการมือ
- `cancelPreorder` ถูก import แบบ dynamic (กัน circular import: `preorderService` import `preorderRoundService` อยู่แล้ว)
- route ส่ง `session.user_id` เป็น `by` — **ต้องมี** ไม่งั้นคืนเงินอัตโนมัติไม่ได้ (ไม่มีผู้ยืนยัน)

### 3.2 ปัญหา 2 — ใช้ `preorder_config` จริง

| ค่า | ก่อน | หลัง | ตรวจที่ |
|---|---|---|---|
| `min_order_qty` | ใช้แค่ของรายการในรอบ (`preorderRoundItem.min_order_qty`) | ขั้นต่ำ = **ค่าที่มากกว่า** ระหว่างรายการในรอบกับตัวสินค้า | `createPreorder` |
| `max_order_qty` | ไม่มีใครอ่าน → ลูกค้าคนเดียวจองได้ถึงโควตาทั้งรอบ | **สูงสุดต่อลูกค้า 1 คนต่อรอบ** — รวมยอดจากพรีออเดอร์เดิมของคนนี้ในรอบเดียวกันที่ยังไม่ยกเลิก (`quantityAlreadyOrdered`) · ข้อความบอกว่าสั่งไว้แล้วกี่ชิ้น เหลือได้อีกกี่ชิ้น | `createPreorder` |
| `lead_time_days` | ไม่มีใครอ่าน | ช่วง **ปิดรับ → วันรับ ≥ lead_time_days** ของทุกสินค้าในรอบ (`assertLeadTime`) | `createRound` (ทุกสินค้า) · `addRoundItem` · `updateRound` ตอนเลื่อน `close_date`/`pickup_date` |

```ts
// ก่อน — createPreorder
if (quantity < (item.min_order_qty ?? 1)) throw badRequest(...);

// หลัง
const minQty = Math.max(item.min_order_qty ?? 1, cfg.min_order_qty ?? 1);
if (quantity < minQty) throw badRequest(`... สั่งขั้นต่ำ ${minQty} ชิ้นต่อรายการ`);
if (cfg.max_order_qty != null && already + quantity > cfg.max_order_qty) throw badRequest(`... สูงสุด ${cfg.max_order_qty} ชิ้นต่อคนต่อรอบ ...`);
```

⚠️ ข้อจำกัด: `max_order_qty` ต่อคนตรวจจากยอดที่อ่านได้ตอนสั่ง — ถ้าลูกค้าคนเดียวกันยิง 2 คำขอพร้อมกันเป๊ะ อาจเกินได้เล็กน้อย
(โควตารวมของรอบยังกันแบบ atomic ตามเดิม ไม่มีทางเกินโควตารอบ)

### 3.3 ปัญหา 4 — กู้คืนรอบได้รายการสินค้ากลับมาด้วย

| | ก่อน | หลัง |
|---|---|---|
| `deleteRound` | ตั้ง `deleted_at` ของรอบ แล้วค่อย `new Date()` ใหม่ให้รายการ (เวลาต่างกันไม่กี่ ms) | ใช้**เวลาเดียวกัน**ทั้งรอบและรายการ |
| `restoreRound` | กู้แค่รอบ (`restoreDoc`) → ได้รอบเปล่า | กู้รายการที่ถูกลบ **พร้อมรอบ** ด้วย: `deleted_at` อยู่ในช่วง `[เวลาลบรอบ, +5 วินาที]` (รองรับข้อมูลเก่าที่เวลาคลาดกัน) · response มี `restored_items` |
| รายการที่แอดมินลบเองก่อนลบรอบ | — | **ไม่ถูกกู้ตาม** (เวลาอยู่ก่อนเวลาลบรอบ) |

> เจอระหว่างเขียนเทส: รุ่นแรกใช้ช่วง ±5 วินาที ทำให้รายการที่แอดมินลบเอง 20 ms ก่อนลบรอบถูกกู้ตามไปด้วย —
> แก้เป็นช่วงไปข้างหน้าอย่างเดียว เพราะรายการที่ลบพร้อมรอบ (ข้อมูลเก่า) มีเวลาเท่ากับหรือหลังรอบเสมอ

## 4. ประเด็นที่ต้องตัดสินใจ (ตัดสินแล้ว 2026-10-01 → ทำตาม §6)

> ด้านล่างคือทางเลือกที่เสนอไว้ตอนตรวจ (2026-09-30) เก็บไว้เป็นเหตุผลประกอบ · **สิ่งที่เลือกจริงอยู่ใน §6.1**

### 4.1 ปัญหา 3 — ใบสั่งผลิตนับพรีออเดอร์ที่ยังไม่จ่ายเงิน

**ตอนนี้:** `createProductionFromRound` นับทุกพรีออเดอร์ที่ `order_status ≠ cancelled` รวม `payment_status: pending`
และ**ไม่มีกำหนดเวลาชำระ / ยกเลิกอัตโนมัติ** → ร้านอาจผลิตให้คนที่ไม่จ่าย

| ทางเลือก | ผล | ต้องทำ |
|---|---|---|
| ก. นับเฉพาะที่จ่ายแล้ว | ผลิตตรงยอดเงินที่ได้ · คนจ่ายช้าหลังสร้างใบผลิตไม่ได้ของ | แก้ filter + แจ้งลูกค้าว่าต้องจ่ายก่อนปิดรอบ |
| ข. นับทั้งหมด (แบบตอนนี้) + ยกเลิกอัตโนมัติคนไม่จ่าย | เช่น ปิดรอบแล้ว X ชั่วโมงยังไม่จ่าย → ยกเลิก + คืนโควตา + แจ้ง LINE | งานเพิ่มใน cron (ใช้โครงเดียวกับเตือนวันรับ) |
| ค. คงไว้แบบเดิม | แอดมินไล่ดูเอง | — |

**แนะนำ:** ข — ร้านเล็กมักรับสั่งก่อนแล้วตามเงินทีหลัง การตัดทิ้งทันทีอาจเสียลูกค้า แต่ต้องมีเส้นตายชัดเจน

### 4.2 ปัญหา 5 — รอบไม่เปิด/ปิดเองตามเวลา

**ตอนนี้:** รอบ `scheduled` ต้องรอแอดมินกดเปิด — ถ้าลืม หน้าเว็บแสดงรอบ แต่ลูกค้าสั่งแล้วได้ "ยังไม่เปิดรับ" ·
เลย `close_date` แล้วแอดมินต้องกดปิดเองก่อนสร้างใบผลิตได้

| ทางเลือก | ต้องทำ |
|---|---|
| ก. cron เปิด/ปิดตามเวลา | เพิ่มงานใน `/api/cron/*` (โครงเดียวกับ preorder-reminders) รันทุก 15–60 นาที: `scheduled` + ถึง `open_date` → `open` · `open` + เลย `close_date` → `closed` + แจ้งร้าน |
| ข. ถือว่า "scheduled + ถึงเวลาแล้ว" สั่งได้เลย | แก้ `assertRoundOrderable` อย่างเดียว ไม่ต้องมี cron — แต่สถานะในหน้าแอดมินจะไม่ตรงความจริง |
| ค. คงไว้แบบเดิม | แอดมินกดเอง |

**แนะนำ:** ก

### 4.3 ปัญหา 8 — ปิดรอบแล้วเปิดกลับไม่ได้

**ตอนนี้:** `closed` เป็นสถานะสุดท้าย — ปิดก่อนกำหนดโดยไม่ตั้งใจต้องสร้างรอบใหม่ (ลูกค้าที่สั่งไว้อยู่รอบเก่า)

| ทางเลือก | เงื่อนไขที่ควรมี |
|---|---|
| ก. อนุญาต `closed → open` | เฉพาะเมื่อ **ยังไม่สร้างใบสั่งผลิต** จากรอบนี้ และยังไม่เลย `close_date` · บันทึก audit |
| ข. คงไว้แบบเดิม | — |

**แนะนำ:** ก (มีเงื่อนไข)

### 6.3 ปิดรอบ → ยกเลิกคนไม่จ่าย → สร้างใบสั่งผลิต (`onRoundClosed`)

| ขั้น | ก่อน | หลัง |
|---|---|---|
| ปิดรอบ | แอดมินกดเอง (ลืม = ค้าง open) | cron ปิดเองเมื่อเลย `close_date` หรือแอดมินกด — **ทั้งสองทางเข้าขั้นตอนเดียวกัน** |
| คนที่ยังไม่จ่าย | ค้าง นับเข้าใบผลิต | **ยกเลิกทุกคนในรอบ** (`allInRound` — ปิดก่อนเวลาก็ถือว่าหมดเวลาจ่าย) ยกเว้นสลิปรอตรวจ |
| ใบสั่งผลิต | แอดมินกดสร้างเอง (`POST /api/admin/production-orders/from-preorder-round`) · **นับทุกคนรวมคนไม่จ่าย** | **สร้างอัตโนมัติ** `production_status: planned` · **นับเฉพาะ paid** · หมายเหตุ "สร้างอัตโนมัติเมื่อปิดรอบ …" |
| วันผลิต | แอดมินกรอก | `productionDateForRound` = `pickup_date − max(lead_time_days)` ของสินค้าในรอบ (อย่างน้อย 1 วัน · ไม่ก่อน `close_date`) |
| สร้างไม่ได้ (ไม่มีใครจ่าย / สินค้าไม่มีสูตร) | — | รอบยังปิดตามปกติ · `production.created: false` + `reason` · แจ้งร้าน |
| สรุปให้ร้าน | — | แจ้งเตือน (เว็บ + LINE) "ปิดรอบพรีออเดอร์ …" : เลขใบผลิต + วันผลิต · ยกเลิกไปกี่ราย · ⚠️ สลิปรอตรวจกี่รายการ |
| response `PATCH …/status` | รอบ | + `close_result: { unpaid: { cancelled, waitingSlip, failed }, production: { created, production_no, production_date, reason } }` |

route เดิม `POST /api/admin/production-orders/from-preorder-round` ยังใช้ได้ (เช่น ยกเลิกใบอัตโนมัติแล้วสร้างใหม่) — นับเฉพาะ paid เหมือนกัน

### 6.4 จ่ายหลังสร้างใบผลิต → บวกเข้าใบผลิต (`onPreorderPaid`)

เรียกอัตโนมัติเมื่อพรีออเดอร์เปลี่ยนเป็น `paid` (`preorderService.setPaymentStatus` — fire-and-forget ไม่ทำให้การยืนยันชำระเงินล้ม)

| สถานการณ์ | ผล |
|---|---|
| รอบยังไม่ปิด | ไม่ทำอะไร — ตอนปิดรอบนับเอง (`not-closed`) |
| รอบปิดแล้ว แต่ยังไม่มีใบผลิต (ตอนปิดไม่มีใครจ่าย) | **สร้างใบผลิตให้** (`created-production`) |
| ใบผลิต `planned` | **บวก `planned_qty`** ของรายการสินค้าเดิม (เฉพาะรายการที่ยัง `pending` และยังไม่ตัดสต็อก) · ถ้าไม่มีรายการของสินค้านี้ → เพิ่มรายการใหม่ด้วยสูตรล่าสุด (`added`) · แจ้งร้านในเว็บ |
| ใบผลิต `in_progress` / `done` | **ไม่แตะ** แจ้งร้าน "จ่ายหลังเริ่มผลิต — เพิ่มรายการผลิตเอง" (`production-started`) |
| สินค้าไม่มีสูตร | แจ้งร้าน (`no-recipe`) |
| เรียกซ้ำ | ไม่บวกซ้ำ — จองฟิลด์ใหม่ `preorders.added_to_production_at` แบบ atomic ก่อนบวก |

### 6.5 เปิด/ปิดรอบอัตโนมัติ (ประเด็น 5) + เปิดกลับ (ประเด็น 8)

**cron `runRoundScheduler`** (แนะนำทุก 15 นาที — ยิ่งถี่ รอบยิ่งเปิด/ปิดตรงเวลา):
1. `scheduled` + `open_date ≤ ตอนนี้` (+ ยังไม่เลย `close_date`) → `open`
2. `open` หรือ `scheduled` + `close_date ≤ ตอนนี้` → `closed` → `onRoundClosed` (§6.3)
3. ยกเลิกพรีออเดอร์ที่เลยกำหนดชำระ (§6.2) — ทุกรอบ

เปลี่ยนสถานะแบบมีเงื่อนไข (สถานะเดิม) → รันซ้ำ / แอดมินกดพร้อมกัน ไม่ทำขั้นตอนปิดรอบซ้ำ

**เปิดรอบที่ปิดแล้วกลับ** `PATCH /api/admin/preorder-rounds/[id]/status { round_status: "open", close_date? }`

| | ก่อน | หลัง |
|---|---|---|
| `closed → open` | ไม่ได้เลย (สถานะสุดท้าย) | ได้ ถ้า **ยังไม่มีใบสั่งผลิต** (ที่ไม่ถูกยกเลิก) ของรอบนี้ ไม่งั้น 409 |
| `close_date` ผ่านไปแล้ว | — | ต้องส่ง `close_date` ใหม่ (อนาคต) มาพร้อมคำสั่ง — ไม่งั้น 409 (cron จะปิดซ้ำทันที · รอบที่ปิดแล้วแก้วันผ่าน `updateRound` ไม่ได้) |
| พรีออเดอร์ที่ถูกยกเลิกตอนปิด | — | **ไม่ฟื้น** — ลูกค้าต้องสั่งใหม่ |

⚠️ **ข้อสังเกต:** เพราะปิดรอบแล้วสร้างใบผลิตอัตโนมัติ เงื่อนไข "ยังไม่มีใบผลิต" จะเป็นจริงแค่รอบที่**ไม่มีใครจ่ายเลย**
ตอนปิด (หรือสินค้าไม่มีสูตร) · ถ้าต้องการเปิดรอบที่มีใบผลิตแล้ว ต้อง**ยกเลิกใบสั่งผลิตก่อน** (ใบผลิตสถานะ `cancelled`
ไม่นับ) แล้วค่อยเปิด — ถ้าอยากให้การเปิดกลับยกเลิกใบผลิตที่ยัง `planned` ให้อัตโนมัติ แจ้งเพื่อปรับได้
